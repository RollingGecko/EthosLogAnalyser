# Changelog

## Unreleased

- **Flight recorder: radio and stick mode**: at the bottom right the recorder shows the transmitter as two square stick fields with a dot each, the axes below (*Gas / Seite*, *Höhe / Quer*) and the values in percent (*−44 % / 0 %*). Positive = right/up; the throttle has no centre (−100 % at the bottom = idle). A channel the log lacks stays at rest and shows *—*; a value older than 2 s shows *—* and a grey dot; a log without stick channels has no radio and the gauges move up. New setting **Data & settings → Flight recorder → Stick mode** (Mode 1–4, default Mode 2, global, stored as `stick_mode` in the settings file; an invalid value counts as 2): switching relabels and redraws the radio at once, the playback keeps running and the position does not change; it survives a restart and a language switch. The bottom row of the layout is shared by radio and (later) aircraft; the radio takes room from the gauges above (battery dial radius 135 px at 1920×1080 / 100 %, 107 px at 150 %, 42 px at 1280×720 / 150 %). The dial unit is no longer drawn on dials with a radius below 50 px (it is in the number as well). Checked against the log of 20 July 2026 at 199.85 s (row 731): QR −263, HR −799, SR 0, Gas −454 show as −26 %, −78 %, 0 %, −44 %. The drawing direction of the elevator is one constant (`POSITIVE_ELEVATOR_IS_UP` in `recorder/stick_modes.py`), to be confirmed in the test build. Moving to the next row takes about 2.7 ms with all gauges and the radio (2.1 ms without the radio's part); switching the stick mode takes about 20 ms. New `recorder/radio.py`, `recorder/stick_modes.py`, `gui/recorder_radio.py`.
- **Flight recorder: cockpit gauges** next to the horizon, in the order altitude, vertical speed, drive, battery: **altitude** relative to the start (round dial, *132 m*), **vertical speed** centred on 0 at 9 o'clock (*+2.4 m/s*, only from a vario sensor), **drive** with RPM as a round dial (*84 000 rpm*) and the throttle as a bar 0–100 %, **battery** with the motor current as a round dial (*63 A*) and the voltage as a bar between the lowest and highest voltage of the flight (*48.6 V · 3.74 V/cell*, the voltage per cell when the battery settings of the aircraft have a cell count). Scales are chosen once per flight from its values (nice values such as 250 m, 120 A, ±10 m/s), so small and large models fill the dials; pointers stop at the ends. Gauges without data are not shown and the others move up (a glider shows altitude and vertical speed); a value older than 2 s shows *—* with a grey pointer. Numbers keep a fixed place and decimals, and get smaller rather than cut off at 125/150 % display scaling. The compact layout puts the gauges in a 2 × 2 grid next to the horizon, the smallest one shows a column of numbers. Checked against the log of 20 July 2026 at 199.85 s (row 731): 102 m, +10.0 m/s, 33 100 rpm, 28 %, 49.0 V · 3.77 V/cell, 5 A – the values of the log columns. Moving to the next row takes about 2.5 ms (before 1.4 ms). New `recorder/dials.py`, `recorder/readouts.py` and `gui/recorder_dials.py`.
- **Flight recorder** (first part): the single flight has two tabs, **Charts** (the page as before; *Save image*, *Enlarge whole page* and *Hide details* moved into this tab, and the details, note and anomalies are shown here only) and **Flight recorder**. The recorder plays the flight back in real time from the time series stored in the database – at once, also while the aircraft is being prepared and for flights without battery data. It shows an **artificial horizon** (sky and ground, pitch ladder every 10°, bank scale and pointer, fixed aircraft symbol, *Bank 23° · Pitch −4°*; inverted flight and rolls across ±180° included; grey with *no attitude data* if the attitude is older than 2 s; hidden with a note if the log has no `R.angle`/`P.angle`) and a **timeline** (click to jump, drag to move, telemetry band, *3:12 / 8:58*, *▶ Play* / *■ Stop*, first row, one row back/forward, end, speed 0.25× to 16×; keys space, arrows, Shift+arrows, Home/End). No interpolation: the last log row holds. The playback ends with the last row that has telemetry (the log part after the landing without telemetry is not shown). The attitude comes only from the attitude sensor; the sign convention of roll and pitch is provisional (positive pitch in the log = nose down, positive roll = right wing down; check in TW-053) and kept in one place (`recorder/flight_track.py`). Changing the flight, the tab, going back to the logbook or to another area stops the playback; a language switch keeps tab, position and speed. Layout follows the window size and the display scaling. New package `recorder/` (track, playback clock, layout, horizon geometry; no Tkinter) and `gui/recorder_page.py`, `gui/recorder_timeline.py`, `gui/recorder_instruments.py`.
- **Code map for developers** (`docs/code-map.md`): one table row per Python file (purpose, names other files use, dependencies), the data flow from log file to database to pages, and a list of where to look for typical changes. The new test `tests/test_code_map.py` fails if a Python file has no row or a row names a file that is gone, so pull requests that add, remove or rename files update the map. No change to the program.
- **Filter with several values**: in the filter of the logbook and the statistics, aircraft, year and month are now lists of check buttons instead of drop-downs, so you can compare e.g. 2024 and 2025, June and July, or two aircraft without changing the filter each time. The field shows what is ticked (*all*, *2024, 2025*, *3 of 5*, *none*); the list stays open while you tick and closes with a click outside or Esc; **Select all** / **Deselect all** at the top. Several values of one field are alternatives (2024 *or* 2025), the fields are combined with *and*; year and month are separate, so years 2024 + 2025 with months 06 + 07 give June and July of both years. Everything ticked means no restriction (a new aircraft or year after an import is included), nothing ticked shows “0 of N flights” without an error. The logbook shows several aircraft (table *Per aircraft*); the statistics still analyse one aircraft and ask for a single one when several are ticked, as with *all*. The scope line, status line and summary name the selection (*Filter: 2024, 2025, months 06, 07* – *3 years* for more than two). Unchanged: *from / to*, *Reset*, the shared filter state, and every number when the filter is on *all* (checked with `examples/logs_2026`: totals, tables and flight list identical to the former version). In the code `FlightFilter.aircraft/year/month` are `None` (no restriction) or a `frozenset`; new `gui/multi_select.py`.
- **No tab “Single flight” any more**: the tab bar shows Logbook, Statistics and Data & settings. A single flight is opened by a double-click on a flight in the logbook and shows on the Logbook tab (which stays highlighted); **‹ Logbook** goes back, and the filter, sorting and list of the logbook are as you left them. Unchanged: the content of the single-flight page, a log that is not a flight cannot be opened, and a language switch or a database change keeps an open flight open. The page is part of the logbook area (`gui/app.py`, `select_page`); a hidden tab was not used because selecting it shows it again.

- **Simpler logbook, nothing cut off**: the bar charts (flights and log duration per month) and the *Group by* tree are removed. The flight list always shows all flights of the filter (with the switches *Show non-flights* and *only with note or anomaly* as before). New table **Per aircraft** (aircraft, flights, flying days, log duration, drawn mAh, with a sum row that equals the totals); it follows the filter and uses the same calculation as the tables per year and per month, which are unchanged. The three tables sit side by side under the totals and the flight list below them has the most space. Column widths and row heights of the tables now follow the font instead of fixed pixels (new `gui/table_fit.py`), so headings and values are no longer cut off at Windows display scaling of 125 % or 150 %: the logbook tables and flight list, the table of the statistics, the flight selection of the single flight and the import report. Unchanged against the former version: totals, tables per year and per month and the flight list (rows, order, values), checked with `examples/logs_2026` and a database with two aircraft; a filter change redraws the logbook page in about 20 ms instead of 110 ms (the bar chart was the slow part). Removed code: `analysis/logbook_groups.py`, `gui/logbook_group_tree.py`, `plots/logbook.py` and their tests.

- **Statistics and single flight ready right after the start**: the per-flight analysis of every flight is now stored in the flight database (schema 3) when a log is imported or calculated again, instead of being repeated for all flights at every program start. With `examples/logs_2026` the statistics are ready about 1.7 s after the start (before 2.9 s); with about 1000 flights in 4 s instead of 43 s. Results are unchanged (flight table, summary, chart data of all statistics pages, single-flight charts and details, CSV export). Only the time series the statistics need are stored (about 47 kB per flight, database of `examples/logs_2026` 6.5 MB instead of 5.0 MB); the single flight works out the others for the flight it shows (about 40 ms). The import takes about 10 % longer. Existing databases are upgraded on opening without importing again: the values are worked out once in the background with progress on *Data & settings* (“Preparing the values for the statistics”), the window stays usable and the statistics work as before meanwhile; notes and anomalies stay. Opening a database now also brings outdated flights up to date when a recalculation of the anomalies was waiting.
- **Statistics from the flight database with the shared filter** (last step of the rebuild): the pages Summary, Battery, Load & flight profile, Drive (with the overall motor curve), Radio & onboard power (with receiver current spikes) and Table show the flights of the database that pass the filter – at once after the start, without *Analyse*. The filter bar (aircraft, year, month, from/to) is shown on top of the statistics and is the same filter as in the logbook: a change in one is seen in the other. Non-flights never count. Aircraft are never mixed: if the filtered flights belong to several aircraft, the statistics ask to choose one in the filter; flights without battery data (e.g. a glider) get a hint instead of the pages. The summary – and the exported report – starts with a highlighted notice that the statistics are still experimental, followed by the filter. Only the page that is shown is drawn; the others when they are opened. The status line on the statistics shows “n of N flights · aircraft · period · filter”. Export (CSV, report and charts) uses the statistics of the filter. Results are identical to the former folder analysis for the same flights (flight table, summary, chart data, CSV).
- **Removed: the folder analysis.** *Data & settings* no longer has *Log data* (folder, *Analyse*, progress bar, model selector), the list of skipped files (the import report of the database replaces it) and *Period from/to* (the filter replaces it). The battery section gets an aircraft selector with the aircraft of the database; battery settings stay per aircraft, with the red hint for an aircraft without settings. Settings files of older versions keep working (folder and period are ignored). Removed code: `analyse_folder`, `analyse_file`, `read_log`, `models_in`, `default_model`, `in_period`, `Params.date_from/date_to`, `Result.skipped/total`, and a few helpers that were no longer used.
- Charts that are redrawn in place (logbook, statistics) keep double-click and right-click to enlarge and the coordinates in the toolbar.

- **Notes and anomalies per flight** (flight database schema 2): every flight can have a free-text note and anomalies with the level *Info*, *Warning* or *Critical* – found by rules or entered by hand, always worded as a hint. *Single flight* has a new section *Note and anomalies* next to the details (save the note, acknowledge or reopen an anomaly, add and delete own entries). The logbook flight list shows a note (✎) and the highest open level (ℹ ⚠ ‼) in its hint column with the texts on hover, and gets the switch *only with note or anomaly*. Rules: comparison with the median of all flights of the aircraft (from 5 flights: short flight, internal resistance, receiver current maximum, RSSI minimum), receiver voltage dip within the flight, limits of the cell chemistry (only with chosen battery settings), a receiver minimum voltage per aircraft (off by default) and the existing limits for receiver current spikes and the current sensor. Each rule can be switched off and its value changed under *Data & settings → Anomalies*. All flights are judged again in the background from stored values only (33 flights 0.03 s, about 1000 flights 0.3 s) after an import, a flight switch and every change of rules or battery settings. Acknowledgements survive recalculations; a clearly changed value (more than 20 %) opens the anomaly again; own entries are never touched. Existing databases are upgraded on opening without losing flights; the receiver voltage values of their logs are worked out once from the stored time series. Standard values and examples in docs/methodology.md.
- *Data & settings* scrolls when the window is not tall enough for all sections.

- New window layout with four areas as tabs at the top: **Logbook** (start page), **Single flight**, **Statistics** and **Data & settings**. *Statistics* holds the pages Summary, Battery, Load & flight profile, Drive, Radio & onboard power and Table as smaller tabs; their content is unchanged and still comes from the folder analysis, as does the logbook. After *Analyse* the app shows *Statistics → Summary*.
- **Single flight from the flight database**: the flight selector lists every flight of the database with date, time, aircraft, duration and drawn charge (newest selected), with *‹ Logbook* to go back. All views and functions are as before (sticks, tooltip, min:s, zoom and pan, enlarging, *Save image*, details, current spikes); charts and details are identical to the folder analysis. Each flight is compared with all flights of its aircraft, with that aircraft's battery settings. The flights of an aircraft are prepared in the background once (about 3 s for 33 flights, the aircraft of the newest flight right after the start); then a flight opens in about 0.7 s. Views without data in the log are hidden; a flight without battery voltage and current (e.g. a glider) shows a note instead of crashing; an empty database shows how to import logs.
- **Logbook from the flight database** (works without the folder analysis): all displays stay (totals, tables per year and month with bar charts, sortable flight list, hint for flights without date or duration, double-click opens the single flight); the flight list gets an *aircraft* column and flight numbers now count per aircraft. New **Group by** tree (time: year → month → aircraft, or aircraft: aircraft → year → month) with flights and flight time per row and a total row; a click on a row restricts only the flight list. New shared **filter** (aircraft, year, month, date from/to) that changes the whole logbook; it is a reusable component (`gui/flight_filter.py`) with one shared state so the statistics can use it later. Logs that are not flights are hidden; **Show non-flights** lists them, and the *Flug* column (☑/☐) switches a log by a click (stored as `is_flight_manual`, the same click undoes it). Possible duplicates get a ⚠ with an explanation on hover. The status line shows the state of the flight database in the logbook and single-flight areas. The statistics pages and the *Period from/to* filter under *Data & settings* are unchanged. Logic lives in pure functions (`analysis/periods.py`, `analysis/logbook_groups.py`, `db/logbook_table.py`) with unit tests.
- Logbook: a double-click on a flight opens it in *Single flight*.
- Internal: `gui/app.py` was split into one module per page (`settings_page`, `statistics_page`, `flight_page`, `logbook_page`, `charts`, `app_settings`, `common`, plus `flight_area`, `flight_cache`, `database_flights` for the database flights); the database section is a class `DatabasePanel`. The cross-flight part of the folder analysis is a function of its own (`analysis.fleet.analyse_flights`), used for the folder and for the database; results unchanged.
- Flight database (first step of the rebuild): new section *Database* at the top of *Data & settings*. Logs are imported from single files or whole folders (with subfolders) into one SQLite file, by default `Documents\EthosLogAnalyser\flugbuch.db`; *New*, *Open*, *Save as* (copy) and *Empty* (with a question). The database used last is opened at program start; on the first start the app offers to import the log folder used so far. The import runs in the background with a progress bar and ends with an import report: new, duplicate (same content, also under another name – skipped), possible duplicate (same aircraft and start time, other content – imported and marked) and unreadable. Every log is imported and marked as flight or not a flight; the detection uses the motor current (rule as before), otherwise altitude, vertical speed or the radio link, so aircraft without a motor or battery sensor are covered. Per flight the database keeps the raw log (lzma), the metrics of the per-flight analysis with the analysis version, the sensors with their role and all time series at full resolution (lossless, compact). `examples/logs_2026`: 33 flights as in the folder analysis, 5.0 MB instead of 18.7 MB. The log files are never changed. The analysis tabs still work on the log folder. Details in docs/database.md.

- New tab *Logbook* (last tab): number of flights, flying days, total log duration, longest and shortest flight, total drawn charge; tables per year and per month with bar charts of flights and log duration per month; a list of all flights (number, date, time, log duration, drawn mAh) that sorts by a click on a column heading. It covers the selected model within the period filter; flights without date or log duration are left out of the totals and counted. "Duration" is the log duration (motor armed to disarmed), not the airborne time. Totals in `analysis/logbook.py` (input: the flight table), so later views can reuse them.
- Several aircraft in one folder: the model is taken from the log file name (the part before the time stamp, e.g. *Viper-Jet*). Logs of different models are never mixed – every analysis covers one model, by default the one with the newest log. With more than one model in the folder a selector *Model* appears under the folder row (tab *Data & settings*), and the status line and summary name the analysed model. Battery settings (cell chemistry, cell count, nominal capacity) are remembered per model; existing settings stay with the first model. The period filter works within the selected model. New column *Model* in the CSV export. With one model in the folder everything looks as before.
- A model without stored battery settings (a new model, or a first start without any battery settings) shows a red hint at the top of the summary, in the status line and below the battery fields in *Data & settings*: choose the cell chemistry and enter the nominal capacity. The assumed LiPo is not treated as a setting; the hint stays (also after a restart) until the cell chemistry is chosen or a capacity is entered. It does not block the analysis.
- In the window *Enlarge whole page* a double-click on a chart (or right-click → *Enlarge this chart*) now enlarges that chart on its own, as on the normal page – in all tabs and in the single-flight views (the time window of the page window is kept). Before, double-click and right-click did nothing there.
- Single flight, attitude view: stick positions on the same time axis as the attitude – roll angle with the aileron stick, pitch angle with the elevator stick (secondary axis in %, both centred on zero), throttle with the rudder stick, then g-load and altitude. Missing or unmoved channels are left out and named in a note. The rotation-rate chart was removed from this view; the rotation rate is still used to assign receiver current spikes to manoeuvres and is listed per spike in the single-flight details.
- Single flight: the battery voltage is shown per cell (V/cell, total voltage / cell count of the analysis) in the chart, tooltip and read-out line, with the limit under load and the minimum resting voltage of the cell chemistry; without a cell count the total voltage is shown with a hint.
- Drive tab: the power-vs-RPM chart shows an overall motor curve from the steady-state points of all flights (median per RPM class with 25–75 % band; run-ups and throttle changes, outliers and classes with too few data are left out). New column *P dev. curve %* (deviation of each flight from the curve) in the table, CSV, summary and single-flight details. Method in docs/methodology.md.
- A chart enlarged on its own keeps its own x label (before, an upper-row chart showed the label of the chart below it, e.g. "Flight no." under the power-vs-RPM curve).
- All times are shown as min:s, from one hour on as h:min:s (charts, tables, summary, timer, single-flight details, reasons for skipped files); one shared formatting function, values rounded to whole seconds. Time axes have ticks on round times. The CSV export keeps the seconds columns and adds a min:s text column after each (`dauer_mmss`, `Timer_mmss`, …).
- Every chart shows a tooltip with the data point nearest to the mouse pointer (series, flight and date or time, value with unit), also on secondary y axes, scatter and bar charts. It is drawn without redrawing the chart, so it stays smooth with long logs.
- Every single chart can be enlarged on its own: a double-click into it (or right-click → *Enlarge this chart*) opens just that chart full screen, with title, explanation, legend, helper lines, markers, trend and twin axes, zoom, pan, tooltip; Esc closes. This also works in the single-flight view (keeps the zoomed time window; *Whole flight* shows the whole flight). *Enlarge whole page* (toolbar button or right-click menu) still opens all charts of a tab. Every chart shown through the shared chart canvas gets this without extra code: the page is drawn again and all other charts are removed.
- The explanation line below a chart title keeps its distance to the title at any chart size.
- Measurement errors are recognised and kept out of the analysis: a stuck current sensor (current at its maximum for the whole flight), voltage dropouts, an impossible resting voltage after landing (below the voltage under load at the end of the flight, e.g. battery unplugged during the measurement), VFR outside 0–100 % and implausible internal resistance. They are listed under *Data quality* instead of being reported as deep discharge or voltage collapse, and no longer distort trends and start values.
- State of health, ageing trend and remaining-life forecast now come from one robust model per metric (Huber-weighted straight line over the flight number), so they no longer contradict each other and single start flights or outliers do not move them. The trend is shown with its 90 % range; without a significant ageing trend, with too few or too scattered values, or with an improving value (e.g. falling internal resistance) no forecast is made and the reason is given.
- The capacity estimate is corrected for its dependency on the depth of discharge and referred to the median depth of the analysed flights (new column *Capacity normalised*). The size of this dependency is estimated only from flights of the same day, so it cannot absorb the ageing trend when later flights go deeper.
- No ageing trend is shown unless it is significant and plausible: otherwise start and current value are the mean level of the period (dashed horizontal line). A rising capacity, or a capacity trend that contradicts the voltage at reference load, is reported as uncertain without forecast.
- Short flights (below 40 % depth of discharge) no longer enter the capacity and internal-resistance trends.
- The robust fit no longer drops values; low values at the end of the series that follow the trend are kept.
- SoH refers to the nominal capacity if one is entered (otherwise to the start value); the change against the start value of the selected period is shown as well.
- Hint when the capacity values form two separate groups (several batteries in the period).
- New period filter (*Data & settings → Period from/to*) to analyse e.g. only the flights of one battery.
- The battery charts draw the robust trend line (dashed mean level if the trend is not significant or uncertain) and the 80 % line relative to the nominal capacity.
- The window title and the new *About* box (*Data & settings*) show the version. Test builds made by GitHub Actions for a pull request or branch show a build tag such as `0.3.0+pr12.abc1234` and *TEST VERSION*; released versions do not.
- Every pull request gets a test EXE for acceptance testing, linked in a pull-request comment and in the run summary (see docs/acceptance-testing.md). Test builds never create a tag or a release.
- docs/releasing.md: the tag is no longer created via *Draft a new release* (that publishes a conflicting release); GitHub Desktop is described as the way without command line.

## 0.3.0

- The user interface is available in German, English and Spanish. The language is chosen under *Data & settings → Language*, switched without restarting and without analysing the logs again, and remembered for the next start. Without a saved choice the app starts in the language of the operating system (English if it is not supported).
- Reports, charts, warnings, reasons for skipped files and exports (file names, text columns of the CSV table) follow the selected language. Dates are shown as dd/mm/yyyy in English and Spanish.
- Analysis results are language-neutral: spike causes, flags, warnings and the source of the end voltage are stored as codes or lazily translated messages and only turned into text when they are shown.
- Tests check that every user-facing text is translated in every catalog, that no translation is unused and that the placeholders match.
- Single flight tab: the view buttons have a row of their own, so the toolbar also fits with longer labels.
- Fixed: in charts with several series (e.g. internal resistance, receiver current) the explanation line overlapped the chart title.
- Releases: pushing a version tag `vX.Y.Z` runs the tests, builds the Windows EXE and publishes it as `EthosLogAnalyser-vX.Y.Z.exe` on GitHub Releases with this changelog section as release notes. The release is refused if tag, version and changelog do not match. See `docs/releasing.md`.

## 0.2.0

- Split the code into the Python package `ethosloganalyser`: `io` (reading), `analysis` (analysis), `report` (texts), `plots` (charts), `gui` (user interface). The analysis is unchanged – verified on 73 log files (35 flights) with identical tables, texts and charts.
- Installation via `pyproject.toml`; start with `ethosloganalyser` or `python -m ethosloganalyser`.
- Automated tests (pytest) for reading, single-flight analysis, receiver current spikes, cross-flight analysis, reports, charts and the GUI; they run on every push on GitHub under Linux and Windows.
- GitHub builds the Windows EXE on every push (`scripts/build_exe.bat`).
- Documentation in `docs/`: usage, methodology, Ethos log format. Documentation, code comments and docstrings are in English; the user interface stays German.
- Fixed: decimal commas in log values were no longer converted with pandas 3.
- Fixed: logs without a date column that run past midnight crashed with pandas 3.
