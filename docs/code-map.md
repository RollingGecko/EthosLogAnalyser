# Code map

A short guide to every Python file of EthosLogAnalyser: what it is for, which names other files use, and what it
depends on. Read this first instead of searching the repository. The test `tests/test_code_map.py` checks that
every `.py` file under `src/ethosloganalyser/`, `tests/` and `scripts/` has a row here and that every row names a
file that exists.

## Layers and data flow

Layers, from the bottom up: `io` (read a log) → `analysis` (pure calculations, no GUI) → `db` (SQLite flight
database, import) → `report`, `plots` and `recorder` (text, charts, playback; usable without a window) → `gui`
(Tkinter). `config`,
`i18n` and `utils` are used by all of them. The GUI never reads log files itself (it starts the import in
`db/importer.py`): everything it shows comes from the database.

```
Ethos CSV log
 → io/ethos_log.read_log_bytes                      DataFrame, time axis, model name from the file name
 → db/importer.import_paths → import_file           duplicate check by hash, one transaction per file
     → db/log_analysis.analyse_log_content          analysis/flight.analyse_frame (per-flight values),
                                                    db/sensor_roles, db/flight_detection, db/signal_metrics,
                                                    db/series_codec (lossless time series)
     → db/flight_store.insert_log                   tables log_file, log_raw, flight, sensor, series
     → db/flight_preparation.store_for_new_analysis prepared values for the statistics
 → gui/flight_cache.FlightCache + gui/database_flights   read the flights back, prepare one aircraft in a thread
 → Logbook:       db/logbook_table → gui/logbook_model → gui/logbook_page   (totals: analysis/logbook)
 → Statistics:    gui/statistics_model (shared filter, one aircraft) → analysis/fleet.analyse_flights
                  → plots/overview + report/text → gui/statistics_page
 → Single flight: gui/flight_area → gui/flight_page   (plots/flight, report/text.flight_detail_lines)
 → Flight recorder: recorder/flight_track.load_track (stored series of one log) → recorder/playback
                  → gui/recorder_page (recorder/layout, gui/recorder_instruments, gui/recorder_dials,
                    gui/recorder_timeline); gauge values and scales: recorder/readouts, recorder/dials
 → Anomalies:     gui/anomaly_controller → db/annotations.recalculate_anomalies → analysis/anomalies.find_anomalies
```

The filter (`analysis/periods.py`, `gui/flight_filter.py`) is one shared state: the logbook and the statistics
show the same setting. Texts are written in German in the code and translated through `i18n.tr` and `locales/`.

Not listed as a row: `src/ethosloganalyser/_build_tag.py` is generated by `scripts/set_build_tag.py` in CI test
builds, is git-ignored and ignored by the test.

## Keeping the map current

Every pull request that adds, removes or renames a Python file, or moves a responsibility from one file to
another, updates this map in the same pull request: add or fix the row of the file (purpose, names other files
use, main dependencies). `tests/test_code_map.py` fails if a file has no row or a row names a file that does not
exist; it does not check the wording, so keep the descriptions true when you change a file.
